# Persistent Storage

By default, everything inside an OvB session is **ephemeral** — when the session ends, the container is destroyed and all files are lost. **Persistent storage** preserves downloaded files across sessions within a workspace.

When enabled, files saved to `/config/Downloads` inside a session are backed by S3 and remain available to every future session in the same workspace. You can also manage these files from outside a session using the [file explorer](/usage/file-explorer).

## Enabling Persistent Storage

Persistent storage requires two flags, both enabled:

1. **Global** — `enable_persistent_storage` in [SiteSettings](/security#index) (admin-controlled)
2. **Workspace** — `enable_persistent_storage` on the workspace (workspace admin-controlled)

When both are on, users see a **Persistent storage** toggle in the launch panel.

> Personal workspaces do **not** receive persistent storage. Only team workspaces are provisioned with an access point.

## Workspace Isolation

Each workspace gets its own S3 access point. A container mounted via one workspace's access point cannot access another workspace's files.

## Closing a Session

<Callout type="error">
  S3 uploads happen **asynchronously** — a file visible inside `/config/Downloads` may not have been uploaded to S3 yet. If you close the session before the upload completes, **the file is lost**.

  After downloading a file you need to keep, **wait at least one minute before closing the session**. Sessions killed by Fargate Spot interruption, OOM, or manual termination get no upload window at all.
</Callout>

## Verifying Files in S3

Files for a workspace are stored under a key prefix matching the workspace UUID:

```bash
aws s3 ls s3://<S3FILES_BUCKET_NAME>/<workspace-uuid>/
```

The bucket name is in `docker/.env` as `S3FILES_BUCKET_NAME`.

## Provisioning Access Points

Access points are created automatically when a new team workspace is created. To provision them for existing workspaces:

```bash
docker compose exec ovb_backend python manage.py backfill_access_points
```

Use `--dry-run` to preview, or `--verify` to check and repair stale access points.

## Deleting Workspace Data

When a workspace is deleted, OvB **automatically** deletes its S3 access point and purges all files (including all historical versions). This happens before the workspace record is removed. The data is **not recoverable** afterward.

Cleanup is best-effort — AWS failures are logged but never block the deletion. If cleanup fails, orphaned data may remain in S3 and can be removed manually via the AWS CLI.
