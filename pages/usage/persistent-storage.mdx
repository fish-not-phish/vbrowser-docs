# Persistent Storage

By default, everything inside an OvB session is **ephemeral** — when the session ends, the container is destroyed and all files are lost. **Persistent storage** is an optional feature that preserves downloaded files across sessions within a workspace.

When enabled, files saved to `/config/Downloads` inside a session are backed by **AWS S3 Files** and remain available to every future session in the same workspace.

## How It Works

Persistent storage uses **AWS S3 Files** — a POSIX-compatible filesystem backed by S3. OvB provisions one shared S3 Files file system per deployment and creates one **access point** per workspace.

When a session launches with persistent storage enabled:

1. The backend resolves the workspace's access point
2. A per-workspace ECS task definition is registered that mounts the access point at `/config/Downloads`
3. The container writes files to `/config/Downloads` as if it were a normal directory
4. S3 Files translates those writes into objects stored under `s3://<bucket>/<workspace-uuid>/`

Files are **durable** once S3 Files has finished uploading them — they persist in S3 after the session ends and are available to the next session in the same workspace. See [Write Behavior & S3 Visibility](#write-behavior--s3-visibility) for the upload lag and the risk of closing a session too soon.

## Workspace Isolation

Each workspace's access point is rooted at `/<workspace-uuid>/` in the shared bucket. The access point enforces this root — a container mounted via workspace A's access point **cannot** traverse above its root to see workspace B's files.

| Layer | Mechanism |
|---|---|
| Access point root | Each access point exposes only `/<workspace-uuid>/` from the bucket |
| Per-workspace task def | Each workspace gets a distinct task definition referencing only its own access point |
| S3 key prefix | Files are physically stored under `s3://<bucket>/<workspace-uuid>/` |

Compromise of one workspace's session does **not** expose another workspace's files.

> Personal workspaces do **not** receive persistent storage. Only non-personal (team) workspaces are provisioned with an access point.

## Enabling Persistent Storage

Persistent storage is gated by two flags, both of which must be enabled:

1. **Global** — `enable_persistent_storage` in [SiteSettings](/security#index) (admin-controlled)
2. **Workspace** — `enable_persistent_storage` on the workspace (workspace admin-controlled)

When both are enabled, users see a **Persistent storage** toggle in the launch panel. If either flag is disabled, sessions launch without the mount and files saved to `/config/Downloads` are ephemeral.

### Provisioning Access Points

Access points are provisioned automatically when a new team workspace is created (if S3 Files is configured). Workspaces created before persistent storage was enabled will not have an access point.

To provision access points for existing workspaces:

```bash
docker compose exec ovb_backend python manage.py backfill_access_points
```

Preview without making changes:

```bash
docker compose exec ovb_backend python manage.py backfill_access_points --dry-run
```

### Verifying Existing Access Points

If an access point was deleted manually in AWS, the database may still hold a stale ARN. Use `--verify` to check existing access points against AWS, clear stale ARNs, and reprovision:

```bash
docker compose exec ovb_backend python manage.py backfill_access_points --verify
```

This command is safe to run at any time — it is idempotent.

## Write Behavior & S3 Visibility

S3 Files maintains a metadata and cache layer in front of S3:

- **Inside the container** — files appear immediately after download. `ls`, `stat`, and reads all work synchronously.
- **In the S3 bucket directly** (`aws s3 ls`) — objects appear **asynchronously**, typically within seconds to a few minutes, as S3 Files flushes batches to S3.

The two views are temporarily inconsistent. A file is readable from inside the container as soon as it is written, but it is only **durably persisted in S3** once Mountpoint has finished uploading it — which happens in the background, typically within seconds to a minute. If the container is destroyed before that upload completes, the file is lost (see [On Session Close](#on-session-close)).

### On Session Close

When a session stops, OvB issues an ECS `stop_task` and returns immediately — it does **not** wait for the container to finish, and there is **no** application-level step that flushes pending writes to S3. The only protection is ECS's default `stopTimeout` (≈30 seconds, since OvB does not configure a longer one) and whatever Mountpoint for S3 manages to upload after it receives `SIGTERM`.

Because S3 Files uploads **asynchronously**, a file that is visible inside `/config/Downloads` may not have been uploaded to S3 yet. If the container is destroyed before that upload completes, **the file is lost** — it never reaches S3. This is especially likely for files downloaded immediately before closing the session.

:::danger
**Files downloaded to persistent storage may be lost if the session is closed too soon.** S3 Files uploads to S3 asynchronously, and OvB does not flush pending uploads before stopping the container. The ECS `stopTimeout` is the only window for in-flight uploads to finish, and it is not guaranteed to be long enough.

**After downloading a file you need to keep, wait at least one minute before closing the session.** Do not rely on persistent storage for the only copy of a file written immediately before close — and keep in mind that sessions killed by Fargate Spot interruption, OOM, or manual ECS termination get **no** flush opportunity at all, regardless of how long you wait.
:::

> Do not assume a file is present in S3 just because it was visible inside the session, or absent just because `aws s3 ls` did not show it during the session. Wait at least one minute after session close before checking.

## Verifying Files in S3

Files for a given workspace are stored under a key prefix matching the workspace UUID:

```bash
aws s3 ls s3://<S3FILES_BUCKET_NAME>/<workspace-uuid>/
```

The bucket name is written to `docker/.env` as `S3FILES_BUCKET_NAME` during Terraform provisioning.

## Failure Modes

If persistent storage is requested but cannot be provisioned, the session launch **fails fast** with a clear error rather than silently launching without the mount.

| Cause | Resolution |
|---|---|
| `S3FILES_FILE_SYSTEM_ARN` not set | Run `terraform apply` and restart the backend |
| Workspace has no access point ARN | Run `python manage.py backfill_access_points` |
| Access point deleted in AWS | Run `python manage.py backfill_access_points --verify` |
| Task definition registration fails | Check backend logs; verify ECS IAM permissions |

:::danger
If a session launches without persistent storage (due to misconfiguration or a disabled flag), files saved to `/config/Downloads` are **ephemeral and unrecoverable**. Always verify the mount is active if persistence is required.
:::

## Deleting Workspace Data

When a workspace is deleted, OvB **automatically** deprovisions its persistent storage. No manual AWS cleanup is required.

The cleanup runs synchronously inside a `pre_delete` signal, before the workspace's database row is removed, and does both of the following:

1. **Deletes the S3 Files access point** — so it can no longer be mounted by future sessions.
2. **Purges all S3 objects under the workspace's prefix** — including every object version **and** delete marker (the bucket has versioning enabled). Both the `<workspace-uuid>/` and `/<workspace-uuid>/` key layouts are purged defensively.

This covers every workspace deletion path: the owner delete endpoint, the leave-as-last-member auto-delete, and Django admin deletion (single-object and bulk).

:::danger
Automatic cleanup deletes **all object versions and delete markers**, not just the current version. After a workspace is deleted, its persistent storage data is **not recoverable** via S3 versioning.
:::

### Best-Effort Semantics

Cleanup is best-effort: each AWS call is attempted independently, and failures are logged but **never block** the workspace deletion. The database row is always removed. If the backend logs a deprovisioning failure (e.g. a transient AWS error or insufficient IAM permissions), orphaned S3 data or a stale access point may remain with no database record pointing to it.

### Manual Recovery

If automatic cleanup failed — or if you want to verify a workspace's data is fully gone — you can clean up manually. First confirm there is nothing left:

```bash
aws s3 ls s3://<S3FILES_BUCKET_NAME>/<workspace-uuid>/ --recursive
```

Then, if anything remains, remove the access point and purge the S3 prefix yourself (including historical versions, which a plain `aws s3 rm --recursive` will **not** delete):

```bash
aws s3files delete-access-point --access-point-id <fsap-...>
aws s3api list-object-versions --bucket <S3FILES_BUCKET_NAME> --prefix "<workspace-uuid>/" \
  --query '{Objects: Versions[].{Key:Key,VersionId:VersionId}}' \
  | aws s3api delete-objects --bucket <S3FILES_BUCKET_NAME> --delete file:///dev/stdin
```

> Personal workspaces never receive persistent storage, so there is nothing to clean up when one is deleted. `DEV_MODE` deployments skip S3 cleanup entirely.
